# NexDesk account API — integration contract

**چکیدهٔ فارسی:** این سند قرارداد کامل بین اپلیکیشن NexDesk و وب‌سایت `nexdesk.ir` است.
هدف: کاربری که در سایت ثبت‌نام می‌کند، با همان نام کاربری و رمز در برنامه هم وارد شود.
برای فاز اول فقط **سه اندپوینت** لازم است (`/api/login`، `/api/currentUser`، `/api/login-options`).
هر بخشی که پیاده نشود، فقط خاموش می‌شود و برنامه کرش نمی‌کند — جدول تخریب تدریجی در انتهای سند.
این سند مستقل است؛ برای پیاده‌سازی نیازی به دیدن کد اپلیکیشن نیست.

---

## 1. Purpose and scope

The NexDesk client ships an account panel: sign in, see the profile, and (optionally)
a shared address book of remote devices. Today that panel talks to a protocol
inherited from the upstream project. This document defines the replacement, served
by `nexdesk.ir`.

Two things are deliberately out of scope:

- **Device connectivity.** Remote sessions do not go through this API at all. They
  use the rendezvous (hbbs) and relay (hbbr) servers on ports 21116/21117. Nothing
  here affects them.
- **Registration.** Users register on the website. This API only authenticates
  them; it does not need a signup endpoint.

## 2. Conventions

| Item | Value |
|---|---|
| Base URL | `https://nexdesk.ir` — no trailing slash, no path prefix |
| Transport | HTTPS only. The client has no way to accept a self-signed certificate. |
| Encoding | UTF-8 JSON, `Content-Type: application/json` |
| Auth header | `Authorization: Bearer <access_token>` |
| Token storage | Client-side only. No cookies, no refresh token, no server session. |
| Timeouts | Client aborts after 12 s per attempt and does not retry automatically. |

**The client always sends `Authorization`** — including the literal `Bearer ` with an
empty token when nobody is signed in. Treat a missing or empty token as
unauthenticated and answer `401`; do not treat it as a malformed request.

**Two device identifiers** appear in most requests:

| Field | Meaning | Stability |
|---|---|---|
| `id` | The device's rendezvous ID (9–10 digits) | Stable per install, changes if the user resets it |
| `uuid` | Base64 of the machine UUID | Stable per install |

Neither is a secret. Both are already public to the rendezvous server.

## 3. Data shapes

### 3.1 `UserPayload` (the profile object)

```json
{
  "name": "vahid",
  "display_name": "Vahid K.",
  "avatar": "https://nexdesk.ir/avatars/vahid.png",
  "email": "vahid@example.com",
  "note": "",
  "verifier": null,
  "status": 1,
  "is_admin": false
}
```

| Field | Type | Required | Notes |
|---|---|---|---|
| `name` | string | yes | Login name. Shown in the account panel. |
| `display_name` | string | no | Falls back to `name` in the UI if empty. |
| `avatar` | string | no | Absolute URL. Empty string is fine. |
| `email` | string | no | Shown in the verification dialog. |
| `note` | string | no | Free text. |
| `verifier` | string \| null | no | Opaque. Only used by the web build; send `null`. |
| `status` | int | yes | `1` = normal, `0` = disabled, `-1` = unverified |
| `is_admin` | bool | no | Defaults to `false` if absent |

Every field is read defensively: a missing key becomes an empty string or `false`,
never an error. Unknown keys are ignored, so you may add fields.

## 4. Phase 1 — the minimum that makes login work

Implement these three and the account panel is functional. Nothing else is required.

### 4.1 `POST /api/login`

Authenticates a user. Two request shapes share this endpoint, distinguished by `type`.

**Step 1 — password login (`type: "account"`)**

```http
POST /api/login
Content-Type: application/json

{
  "username": "vahid",
  "password": "…",
  "id": "123456789",
  "uuid": "b3JkZXI…",
  "autoLogin": true,
  "type": "account",
  "deviceInfo": { "os": "android", "type": "client", "name": "SM-A525F" }
}
```

`deviceInfo` is generated by the client and may contain any of `os`, `type`, `name`.
Store it if you want a device list; ignore it otherwise.

**Success:**

```json
{
  "type": "access_token",
  "access_token": "opaque-string",
  "user": { "name": "vahid", "status": 1, "is_admin": false, … }
}
```

`type` **must** be the literal `"access_token"`. The client compares it before it
accepts the token, and any other value leaves the user signed out.

**Two-factor / email verification instead of a token:**

```json
{
  "type": "email_check",
  "tfa_type": "email_check",
  "secret": "opaque-echo-token",
  "user": { "email": "vahid@example.com", … }
}
```

The client opens a verification dialog and shows `user.email`. `secret` is opaque:
it is echoed back in step 2 and never interpreted.

**Step 2 — verification code (`type: "email_code"`)**

```http
POST /api/login

{
  "verificationCode": "482913",
  "tfaCode": null,
  "secret": "opaque-echo-token",
  "username": "vahid",
  "id": "123456789",
  "uuid": "b3JkZXI…",
  "autoLogin": true,
  "type": "email_code",
  "deviceInfo": { … }
}
```

`tfaCode` carries a TOTP code when `tfa_type` was `"tfa_check"`, and is `null` for an
email code. `verificationCode` always carries what the user typed. A successful
response has the same `access_token` shape as step 1.

If you do not want to implement verification, answer step 1 with `access_token`
directly — the second step is only reached when step 1 returns `email_check`.

### 4.2 `POST /api/currentUser`

Called at startup when a token is already stored, and after any 401 recovery. **It is
a POST with a body**, not a GET.

```http
POST /api/currentUser
Content-Type: application/json
Authorization: Bearer <token>

{ "id": "123456789", "uuid": "b3JkZXI…" }
```

**Success** — a `UserPayload` at the **top level**, not wrapped in `user`:

```json
{ "name": "vahid", "display_name": "Vahid K.", "status": 1, "is_admin": false }
```

Status codes the client treats specially:

| Status | Client behaviour |
|---|---|
| `200` | Profile refreshed |
| `401` | Full sign-out: clears the token **and** the address book and group caches |
| `400` | Clears the token, keeps cached lists |
| other | Shows the error in the address-book and group tabs |

If the token is valid but the account is gone, prefer `401` — that is the path the
client recovers from cleanly.

### 4.3 `GET /api/login-options`

Lists third-party identity providers. **Return an empty JSON array** for phase 1:

```http
GET /api/login-options

[]
```

The response must be valid JSON. An HTML 404 page makes the client throw inside its
JSON decoder and show a generic network error; `[]` shows nothing extra and leaves
username/password login untouched.

The client accepts two array forms if you add providers later:

- `["oidc/google", "oidc/github"]` — name-only, icons come from the client
- `["common-oidc/[{\"name\":\"google\",\"icon\":\"<svg…>\"}]"]` — name plus inline SVG

### 4.4 `POST /api/logout` (optional, recommended)

```http
POST /api/logout
Authorization: Bearer <token>

{ "id": "123456789", "uuid": "b3JkZXI…" }
```

The client waits 2 seconds and ignores every outcome — it clears local state either
way. Returning `404` is acceptable. Implement it only to invalidate the token
server-side.

## 5. Error contract

This is the part most easily got wrong.

- On failure, return the **HTTP status** you mean, plus `{"error": "…"}`.
- `error` is displayed to the user **verbatim**, so it must be a short human-readable
  sentence in the user's language — not a code, not a stack trace.
  - Good: `"نام کاربری یا رمز عبور نادرست است"`
  - Bad: `"ERR_INVALID_CREDENTIALS"`
- `200` with an `error` field is treated as a failure, so do not use it for success.
- A non-JSON body produces a bare `HTTP <code>` toast and a generic error.

Recommended statuses: `400` malformed request, `401` bad credentials or expired
token, `403` disabled account, `429` rate-limited, `5xx` server fault.

## 6. Phase 2 — address book and device groups (optional)

The client shows a device list when these exist. **Skip them entirely for phase 1**;
the UI degrades cleanly (see §8). All require the Bearer header. Bodyless POSTs must
send `Content-Length: 0`.

| Endpoint | Response | Meaning of `404` |
|---|---|---|
| `POST /api/ab/settings` | `{"max_peer_one_ab": 100}` | shared address book unsupported |
| `POST /api/ab/personal` | `{"guid": "…"}` | fall back to legacy mode |
| `POST /api/ab/shared/profiles?current=1&pageSize=100` | `{"total": 1, "data": [{"guid","name","owner","note","info","rule"}]}` | none |
| `POST /api/ab/peers?current=1&pageSize=100&ab=<guid>` | `{"total": n, "data": [Peer]}` | none |
| `POST /api/ab/tags/<guid>` | `[{"name":"office","color":16711680}]` — a bare array | none |

Paging rule: the client stops when `current * pageSize >= total`, so **`total` is
required**; `data` may be omitted.

Mutations follow the same pattern: `POST /api/ab/peer/add/<guid>`, `PUT
/api/ab/peer/update/<guid>`, `DELETE /api/ab/peer/<guid>`, and the `tag/*`
equivalents. Success is `200` with an empty body.

**Legacy fallback:** if both `/api/ab/settings` and `/api/ab/personal` return `404`,
the client calls `GET /api/ab`, which must answer `200` with the literal `null` for an
empty book, or `{"data": "<JSON string>", "licensed_devices": n}`.

`Peer` fields: `id`, `hash`, `password`, `username`, `hostname`, `platform`, `alias`,
`tags`, `forceAlwaysRelay` (`"true"`/`"false"` as a string), `rdpPort`, `rdpUsername`,
`loginName`, `device_group_name`, `note`, `same_server`.

### Device groups

```
GET /api/device-group/accessible?current=1&pageSize=100  → {"total":n,"data":[{"name":"…"}]}
GET /api/users?current=1&pageSize=100&accessible=&status=1 → {"total":n,"data":[UserPayload]}
GET /api/peers?current=1&pageSize=100&accessible=&status=1 → {"total":n,"data":[PeerPayload]}
```

`PeerPayload` = `{id, info:{os, device_name, username}, status, user, user_name,
device_group_name, note}`. A `401` anywhere here triggers the same global sign-out as
§4.2.

## 7. Phase 3 — OIDC (skip unless you need social login)

```
POST /api/oidc/auth
{ "op":"google", "id":"…", "uuid":"…", "deviceInfo":{…}, "apiDomain":"https://nexdesk.ir" }
→ { "code":"<opaque>", "url":"https://…" }

GET /api/oidc/auth-query?code=<opaque>&id=…&uuid=…
→ { "body": "<JSON string of {access_token,type,tfa_type,secret,user}>" }
```

There is **no redirect URI** back into the app. The client opens `url` in the system
browser and polls `auth-query` once per second for up to 3 minutes. Note that `body`
is a **JSON-encoded string**, i.e. double-encoded.

## 8. Graceful degradation

What happens when a piece is missing. Nothing here crashes the client.

| Missing endpoint | User-visible effect |
|---|---|
| `/api/login` | Sign-in fails with the error text. Everything else works. |
| `/api/currentUser` | Error banner in the address-book/group tabs after a restart |
| `/api/login-options` | Login dialog shows an error and a Retry button; password login still works |
| `/api/logout` | Nothing |
| `/api/ab/*` | Empty address book, no error if `404` on settings+personal |
| `/api/device-group/accessible` | No groups, silent |
| `/api/users`, `/api/peers` | Group tab shows an error banner |
| `/api/oidc/*` | Irrelevant while `login-options` returns `[]` |

## 9. Server-side requirements

1. **Hash passwords** with Argon2id or bcrypt (cost ≥ 12). Never store plaintext.
2. **Opaque tokens.** Random ≥ 32 bytes, stored hashed. No JWT needed; the client
   treats the token as an opaque string.
3. **Expiry.** Tokens should expire (30 days is reasonable). An expired token must
   return `401`, not `403` — `401` is the path that clears client state.
4. **Rate-limit `/api/login`** per IP and per username. `429` is understood.
5. **No secrets in responses.** The `user` object is visible to the user only.
6. **CORS** is irrelevant: the client is native, not a browser.

## 10. Acceptance tests

Run these against the deployed API before shipping the app build.

| # | Test | Expected |
|---|---|---|
| 1 | `GET /api/login-options` | `200`, body `[]`, `Content-Type` contains `json` |
| 2 | `POST /api/login` with a valid user, `type:"account"` | `200`, `type:"access_token"`, non-empty `access_token`, `user.status` = 1 |
| 3 | Same with a wrong password | `401` (or `400`), `{"error": "<sentence>"}` |
| 4 | `POST /api/currentUser` with that token | `200`, a top-level `UserPayload` |
| 5 | Same with a garbage token | `401` |
| 6 | Same with no `Authorization` header | `401` |
| 7 | `POST /api/login` twice with `autoLogin:true` | Both succeed; the second token may replace the first |
| 8 | Disable the account, then call `/api/currentUser` | `401` or `403`, and the client signs out |
| 9 | Response bodies | Valid UTF-8 JSON in every case, including errors |

## 11. Reference implementation sketch

Minimal PHP outline; any stack works.

```php
// POST /api/login
$in = json_decode(file_get_contents('php://input'), true);
$user = find_user_by_name($in['username'] ?? '');
if (!$user || !password_verify($in['password'] ?? '', $user['password_hash'])) {
    http_response_code(401);
    echo json_encode(['error' => 'نام کاربری یا رمز عبور نادرست است'], JSON_UNESCAPED_UNICODE);
    exit;
}
$token = bin2hex(random_bytes(32));
store_token($token, $user['id']);
echo json_encode([
    'type'         => 'access_token',
    'access_token' => $token,
    'user'         => public_user($user),
], JSON_UNESCAPED_UNICODE);
```

```php
// POST /api/currentUser
$hdr = $_SERVER['HTTP_AUTHORIZATION'] ?? '';
if (!preg_match('/^Bearer\s+(\S+)$/', $hdr, $m) || !($uid = lookup_token($m[1]))) {
    http_response_code(401);
    echo json_encode(['error' => 'نشست منقضی شده است'], JSON_UNESCAPED_UNICODE);
    exit;
}
echo json_encode(public_user(find_user($uid)), JSON_UNESCAPED_UNICODE);
```

`public_user()` must emit exactly the fields in §3.1 and nothing sensitive.
